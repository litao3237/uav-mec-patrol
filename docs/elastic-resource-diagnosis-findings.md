## 实验目标与可靠性边界

已完成多轮 ALNS 邻域与参数敏感性验证，但仍无法区分高负载固定方案的真实时序/资源冲突与纯数值求解问题。本实验**不增加任何 ALNS 后处理或修改原先的离散结果**，只读取已归档的 [参数敏感性原始资源结果](https://github.com/litao3237/uav-mec-patrol/actions/runs/38043248604)，恢复各方案原始任务归属、路径、上传接触、卸载模式和批次，重建**相同**凸资源模型 P1-R，并在特定原硬约束旁增加显式弹性变量。

**模式 A `qos_only`：** 放松任务截止时间、系统平均时延、巡检周期、UAV 电池约束；**保持 MEC 站点总 CPU/带宽、所有本地 FIFO、MEC FIFO/EDF、上传速率及物理 CPU 上界为原来的硬约束**。

**模式 B `qos_plus_mec_capacity`：** 在模式 A 基础上，为站点总 CPU/带宽添加可计量的反事实容量松弛，用来观察硬件扩容与时限放松的权衡；扩容后的点不是原物理实例的可行解。

目标是最小化各硬约束标准化后的松弛之和（无量纲）；可将原 P1-R 正向尺度转换回“截止时间不足多少秒”“MEC 容量不足多少 GHz/MHz”“电池预算不足多少焦耳”等。但必须注意：**最小加权松弛不是严格的最小不可行约束集（IIS），也不能自动将最大的松弛约束解释为唯一因果瓶颈。**

数值接受只采用求解器 `optimal` 且原始硬约束与所有弹性化约束均满足提前冻结的归一化数值容差；`optimal_inaccurate` 或求解器无法满足残差时必须计为**诊断不确定**，不能补造冲突。

## 一、全部结果及来源

- **五个独立工作块：** K50/S61 为低负载对照；K80/S61、S62、S63、S64 为压力对照；
- 7 种物理参数配置，原 B-ALNS 与原 ESI-ALNS 两种离散输出，每场景 2 个算法随机种子；
- **140 条源方法结果**，其中部分 B/ESI 共享完全相同的离散结构，去重后为 **98 个唯一（实例、离散方案）对**。不能误称为 140 个独立场景。
- 两种弹性模式每条均返回满足冻结数值可信标准的 `optimal`，**140/140**；
- 原严格 Stage-1 通过的 **88 条**，弹性模型无一出现超过 0.002 归一化阈值的错误冲突；
- 原 Stage-1 未通过的 52 条中，**50 条**取得明显正的最小弹性松弛，另外 **2 条**几乎为零（见数值问题讨论）。

## 二、K80：约束族归因结果

表中“正松弛”指模式 A 返回可信 `optimal`，标准化总弹性松弛和 **> 0.002**。数值大小随诊断权重变化，不能作为跨场景物理严重度的统一尺度。

| K80 物理配置 | 原严格 Stage-1 合格 / 16 | 可信正弹性冲突 / 16 |
|---|---:|---:|
| 原基准 | **16/16** | 0 |
| 计算密度 ×1.5 | **8/16** | **8** |
| 计算密度 ×2 | **4/16** | **12** |
| 真实截止时间 ×0.9 | **6/16** | **10** |
| 真实截止时间 ×0.8 | **2/16** | **14** |
| MEC 总带宽 ×0.5 | **12/16** | **4** |
| MEC 总带宽 ×1.5 | **12/16** | **2** |
| **全部** | **60/112** | **50/112** |

源实验的 52 条未严格合格状态分别为：
- 44 条 `infeasible_precheck`，对应先前独立的乐观必要时延下界不合格；
- 2 条 `infeasible`；
- 6 条 `optimal_inaccurate`。

其中 4 条 `optimal_inaccurate` 仍具有显著弹性时间冲突，**另外 2 条没有任何明显弹性松弛**。后两条是同一参数工况（K80/S62/A112/MEC 带宽 ×1.5）的 B/ESI 重复结构。故即使原求解器标记 `optimal_inaccurate`，也不能直接推断数学不可行；至少这一个结构值得单独做数值重试和原始残差核验。

### 时间冲突的结构定位

本轮可信正松弛的 50 条 K80 源方法结果中：
- **50/50 的第一位最大标准化松弛都来自某一任务的 `deadline` 约束**；
- 对应前驱结构 32 条为 **UAV 本地 FIFO 计算队列**，18 条为 **MEC 上传批次 EDF / 同一 UAV-MEC 虚拟 FIFO**。

该模式有明确的建模解释：提高计算密度或缩短任务时限后，被直接放松的最紧硬约束常是某个任务完成期限，但致使它迟到的原因可能是本地 FIFO 前驱任务、上传接触顺序、MEC 批次排队或资源容量竞争。上面的 32/18 是**对应任务计算模式与前驱类型**，不是严格的“本地 FIFO 造成 32 次、MEC CPU 造成 18 次”的因果证据。

模式 B 额外放松 MEC 容量后，绝大多数结构的时间冲突并未消失。K80、计算密度 ×2 的工况出现一些 MEC CPU 容量松弛（原始 B 结构 8 条的 `mec_cpu_cap` 归一化松弛和约 0.242），但**单纯的“期限+硬件”联合加权松弛目标仍无法证明是资源容量不足还是路径/时序本身受限**。后续需要更清晰的单独容量反事实或固定对偶敏感性诊断。

## 三、K50 对照

在仅作为数值对照的 K50/S61 场景（7 物理配置×2 算法×2 算法种子）中：
- **28/28** 原始 Stage-1 严格合格；
- **28/28** 新弹性诊断可信；
- QoS-only 与 QoS+capacity 两组的归一化冲突均接近 **零**；
- 没有凭空把原本可行的离散解误标为强约束冲突。

这帮助确认模型的“硬约束集合、松弛物理量尺度、原始数值模型”与既有严格可行性结果基本一致，但 K50 只检查了 1 个场景，仍非大样本保证。

## 四、为何比直接增加 ALNS 算子更有用？

这是第一轮将高负载失败的原因**从“求解不合格”细化到“哪个任务迟到、其计算模式、阻塞前驱、同一 MEC 批次以及所需松弛秒数”**的诊断实验。

当前结果支持这样的算法设计假设：

> 高负载下，修改唯一一个违规任务不一定能处理完整依赖链；应该先分析本地 CPU FIFO 与 MEC 批次 EDF/FIFO 的计算前驱、接触位置及关键资源容量，在有限计算预算内联合修复真正阻塞的部分。

但是**本实验没有进行任何新的离散修复，更没有证明新方法在等时间预算下取得了更好能耗或更高可行率**。诊断策略的加权目标对结果有影响，不能直接把当前标准化松弛大小当作启发式修复价值。

## 五、下一阶段的明确验证

1. 冻结当前弹性诊断实现，在已知不合格 D 上**分别**保持全部 QoS 硬约束、仅允许 MEC 容量松弛（独立反事实），与已验证的“只放松 QoS”结果对照，更明确区分能否纯靠增配带宽/CPU 修复。
2. 基于高贡献 `deadline::task` 及其本地 FIFO/MEC EDF 前驱生成定向任务/接触/卸载修复候选，并对**相同 D** 比较：无诊断、旧乐观 LB、队列 LB、弹性诊断引导、随机同等预算修复。
3. 只接受原始 Stage-1/Stage-2 和两套独立时序残差全部通过的候选；完整记录诊断建模/求解时间、生成时间、精确候选评价次数和成功率。
4. 最后在未参与这些机制设计的独立场景上进行相同端到端时间预算验证，才判断是否有条件作为论文核心贡献。
