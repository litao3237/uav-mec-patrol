# 高负载严格不可行的离散搜索状态：约束证书引导修复诊断

**GitHub Actions:** https://github.com/litao3237/uav-mec-patrol/actions/runs/38046165343  
**实验分支：** `experiment/highload-feasibility-rescue`  
**运行源提交：** `0d8ef3736fef9d3488a483d6c4953fa0b238ae6d`  
**结果：** 全部冒烟、4 个独立场景块与自动汇总均运行成功，无程序异常。原始 `develop` 未改动。

## 1. 数据选取与对照

直接从已存储的 [参数敏感性实验](https://github.com/litao3237/uav-mec-patrol/actions/runs/38043248604) 恢复 **K80 在计算密度 ×1.5 / ×2、实际截止时间 ×0.9 / ×0.8** 下的 B-ALNS 失败离散方案，不重新生成初始解、不重新执行算法以择优挑样本，也不把共享原始轨迹的 B/ESI 复制当成独立实验。

样本共 32 个“场景×算法种子×压力配置”：
- 其中 **21 个** `stage1_status=infeasible_precheck`，具有违反任务完成时间/飞行周期等**必要乐观下界**的结构证书，是本轮修复对象。
- 其它 **11 个**（包括本来合格或其它求解器状态）均保留为排除/覆盖记录。特别不能把 `optimal_inaccurate` 错误归类为数学不可行。

对相同的 21 个失败结构依次独立尝试：
1. **原有 MEC greedy repair：** `build_mec_assisted_initial_solution`，默认实现，不更换路线。
2. **Guided reorder：** 根据乐观截止时间 LB 的超额任务优先考虑将对应任务调到所在 UAV 路径更早的位置。
3. **Guided contact/mode：** 提前合法 MEC 接触点，或调整违规任务的本地/已有接触卸载选择。
4. **Guided joint：** 同时开放上面两类邻域。

Guided 三种方式使用同样的探测预算：beam width 2、最多两步结构调整、每方法严格评价不超过 3 个满足必要乐观预筛选的候选。最终只有**Stage-1+Stage-2 及两条时序独立残差全部验收**才算修复成功。原始 MEC greedy 的候选枚举次数与 guided 不同，耗时与调用数必须作为对照信息，不应作为等时间算法胜负。

## 2. 21 个严格失败结构的全部结果

| 工况 | 结构失败样本 | 原 MEC greedy（乐观预检恢复 / 严格恢复） | 任务重排 | 接触/卸载 | 联合 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 计算密度 ×1.5 | 4 | **0 / 0** | 2 / 0 | 2 / 0 | **4 / 0** |
| 计算密度 ×2.0 | 6 | **0 / 0** | 2 / 0 | 2 / 0 | **4 / 0** |
| 截止时间 ×0.9 | 5 | **0 / 0** | 0 / 0 | **3 / 1** | **3 / 1** |
| 截止时间 ×0.8 | 6 | **0 / 0** | 1 / 0 | 2 / 0 | **4 / 0** |
| **合计** | **21** | **0 / 0** | **5 / 0** | **9 / 1** | **15 / 1** |

表中 `a / b` = 该类修复至少生成一个通过**必要乐观预检**的候选数量 / 最终经过两阶段独立数值验收的修复成功数。不能把 15/21 的预检通过率包装成 15/21 的真实可行修复率。

原有 MEC greedy 在这 21 个失败结构上 **21/21 完全没有改变离散结构**，因而没有一个通过必要预检或 Stage-1/Stage-2。这说明其当前控制逻辑（只对代理违反进行逐步局部卸载/加接触修复，在代理没有改善时停止）并不适合解决此类正式连续资源模型下的高压不可行状态。

### 唯一严格修复成功的例子

**K80、S61、A112、截止时间 ×0.9：**
- 初始方案具有无法通过必要乐观时间下界的任务/接触结构；
- 将原有上传接触 `G_U4_3` 从路径位置 **22 调整到 20**；
- 此一修改得到 **Stage-1、Stage-2 及两条时序残差**通过的合格解；
- Stage-1 UAV 总能耗约 **247.32 kJ**。

这显示接触重定位即使在简单能耗消融实验中总体贡献有限，也可能对高负载的**可行性修复**具有决定性作用。因此不应该仅根据原始的能耗消融结果删除该类操作。

## 3. 更重要的负面证据

联合两步修复在 21 个原本必要下界不合格的结构中，最多能让 **15 个**至少存在一个通过乐观预检的候选，但其中最终只有 **1 个**满足真实完整资源分配。

该差距很大，说明：

**从“各任务即使假设占有最大 CPU/带宽也不会迟到”推进到“在共享 MEC CPU/带宽、真实本地 FIFO、MEC 批次 FIFO/EDF、巡检周期和电量限制下联合可行”之间仍存在主要鸿沟。**

仅仅改善单任务乐观时间下界，或者在已有接触点上改变计算模式，通常远远不够。下一步需要**整体的批次/接触与资源压力识别，必要时联合更改 UAV 任务归属和路线**，而不是再扩大简单同类邻域次数。

## 4. 学术与工程决策

- 不合并 `develop`、不修改论文主实验参数，不把失败结构的后验修复计入“算法等时间赢了”的结论。
- **保留原有接触重定位和接触删除能力**，因为它们对可行性和能耗的作用不同；应设计按场景约束压力激活的阶段性用途。
- 新算法创新更合适的核心问题是：**在没有严格可行 Stage-1 锚点时，如何依据真实资源瓶颈构造路径—接触—卸载耦合修复，并恢复一个合格结构？**
- 推荐下一步先在独立诊断中建立**凸子问题弹性约束（elastic-slack）**，确定完整调度中究竟是 deadline、cycle、带宽/CPU、还是电池容量冲突，再基于该信息修改离散结构；否则仅靠乐观 LB 排序的候选会大量通过预检却在真正资源求解时失败。
- 以上只有 4 个独立场景和 21 个从中选择的失败离散结构，结果仅支持机制假设。未来应在新场景及相同端到端预算下与原 B-ALNS/ESI 比较完整严格合格率、能耗和超时情况。
