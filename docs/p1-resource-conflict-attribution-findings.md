## 一、审计协议

从原 P1 归档恢复 22 个源 `infeasible_precheck` 固定 D，验证所有物理实例、离散方案 SHA-256 后，**再次执行相同的原子+跨 UAV 四步搜索，beam=2，候选生成软上限4s**。只有为了诊断候选截断错误，才把精确候选评价个数从**原始3**额外拓展至**最多8**；原来的算法没有得到额外求解机会。

- **Stage-1**：用原始 CVX/资源模型和原验收门槛独立重新求解每个入选候选；扩展名额中 Stage-1 合格者才进一步通过**原始 Stage-1+Stage-2 和时序残差**严格重验。
- **结构追踪**：记录每个候选的 SHA-256、父状态 SHA-256、完整原子/传统算子祖先路径、必须预检、真实状态、排序元组与资源诊断。
- **QoS 弹性诊断（只诊断）**：MEC CPU/带宽容量保持硬约束，仅松弛任务截止、平均时延、周期与电池，冻结原固定 D 和 FIFO/EDF、上传、物理资源模型。
- **仅 MEC 容量扩容反事实（只诊断）**：时序/QoS 等所有其它约束仍为硬约束，仅允许 MEC 站点 CPU 和带宽容量增加。此类“假想扩容”绝不算真实问题可行解，更不是物理设备扩容方案。
- 可信数值诊断必须状态 `optimal`、全部剩余硬约束与弹性约束的归一化残差小于预设容差；纯 `infeasible` 和 `optimal_inaccurate` 不等于形式化不可行证书。

### 审计完整性

全部 **22/22** 源固定结构原始精确候选**前三个标签完全一致**，没有短名单/路径身份漂移；未出现程序异常，数值模型阳性对照无假冲突。

## 二、硬必要条件指向任务截止时间，不是平均时延/巡检周期

22 个失败固定 D 均存在完成期限的必要队列时间下界超标；其中 **21/22** 涉及 MEC 卸载任务，**18/22** 涉及本地计算任务（两类高度重叠）。**0/22** 是平均时延或巡检周期必要下界超标导致。

注意：原初始旧 task-only 预检仅指出 21 个源 D 存在卸载任务超时、1个有本地任务超时；新的 FIFO/EDF 队列感知必要下界发现了更多同时发生的本地排队冲突，两者口径不同。

按高压力情况，原 P1 共同源中（原始原子联合方法）：

| 物理压力 | 失败源结构 | 至少有一个预检通过候选 | 原始前3严格恢复 |
|---|---:|---:|---:|
| 计算密度 ×1.5 | 4 | 3 | 2 |
| 计算密度 ×2.0 | 8 | 4 | **0** |
| 截止时间 ×0.9 | 3 | 3 | 2 |
| 截止时间 ×0.8 | 7 | 1 | **0** |
| **合计** | **22** | **11** | **4** |

两种失败机制必须分开处理：较紧截止时间下，更多源结构**连一个必要预检合格离散候选都找不到**；计算密度×2则即使找到一些乐观通过的候选，原严格 Stage-1 仍然无法合格。不能只对全部样本统一“多生成候选”或“调参数”。

## 三、候选排序的因果级案例：S85/compute×1.5/A125

这是这一轮最明确的算法瓶颈证据。

原子搜索返回了**至少8个**必要队列预检通过候选。其排序主指标**完全相同**：

- `n_reasons=0`
- `total_excess_s=0`
- `route_distance_m=11878.255204372252`，8个严格一致。
- 因此原排序最终退化到候选**名称字符串的字典序**，`bundle_new_contact` 在 `bundle_reuse_contact` 之前，与真实 MEC 资源可行性无关。

| 原全局排名 | 候选操作 | Stage-1 状态 | 额外严格 Stage1+2结果 |
|---:|---|---|---|
| 1–4 | 四个 `bundle_new_contact` 新建接触/双任务卸载 | **4个 infeasible** | 不合格 |
| **5–8** | 四个 `bundle_reuse_contact` 复用原接触的双任务卸载 | **4个 optimal** | **4个全部两阶段严格合格** |

原正式方法只允许前3个精确评价，所以**原子分支此例恢复失败**；诊断额外检查的第5–8位全部成功。最优额外诊断候选 rank8 能耗 **236392.30 J**（不应拿它与同样3次求解的基线公平比较）；原普通四步恢复候选能耗 **236569.67 J**。

尤其是**候选1**和**候选5**，其父状态 SHA-256 完全相同：

`931c0a8ea65f4f9823e7d9ad42720a15014754b7ad988bf540aacd7e6e0185db`

均先执行 `cross_uav_fifo_relocation::S68->U5@12`，下一步都调整 **S41+S18** 两任务，唯一区别是**新建接触**还是**复用现有 G_U5_1 接触/批次**。两者代理航线距离一样，前者数值 `infeasible`，后者严格可行。这是等代理分数下候选选择错误的**直接、可复现对照**，而不是“新原子算子完全无用”。

候选1的真实原模型弹性诊断发现 `deadline::S48` 需约 **2.25 秒**松弛；仅 MEC 容量扩容反事实求得 E1 CPU 约**额外 0.181 GHz** 可以使固定结构在数值上满足原 QoS。而复用现有接触的合格候选 QoS 最小松弛约 `4.4e-10`，几乎为零。

这说明 MEC 接触/批次的资源时序差异没有体现在当前代理键中：**没有改变巡航里程，也可能从严格可行变为严格不可行**。

## 四、8个被选中却无法通过 Stage-1 的连续资源负对照

共对每个存在严格失败候选的源 D 的**一个代表性失败候选**进行两种弹性诊断，共8条，不是8个独立场景。结果：

- 8/8：`qos_only` 和 `mec_capacity_only` 都获得通过数值残差审计的可信 `optimal`。
- **7/8**：QoS-only 总归一化松弛 **>0.002**；第8条约0.001965（**对应实际0.884秒**的任务截止时间松弛，并非数学上完全零冲突）。
- 8/8：仅放松 MEC 容量、其余时序/QoS硬保持，也需要**严格正的 CPU/带宽容量扩容松弛**。
- 8个 QoS-only 的最高松弛均来自某个任务的 `deadline`，不是电池/周期。
- 所有数值阳性对照（原 Stage-1 严格合格者）QoS 松弛均接近0，无错误的明显冲突。

| 示例源 D | 不合格候选原硬约束冲突（QoS-only） | 仅扩容 MEC 的反事实诊断 |
|---|---|---|
| S85 compute×1.5 A125 | S48 截止时间约差 2.25s | E1 CPU +0.181 GHz |
| S85 compute×2 A125 | S41差25.24s、S48差21.21s等 | E2 CPU +3.536GHz、E1 CPU +1.297GHz、E2带宽 +0.395MHz |
| S86 compute×2 A126 | S39约差102.20s、S68约差100.08s等 | E2 CPU +5.983GHz |
| S86 deadline×0.9 A125 | S10约差0.884s | E2 CPU +0.328GHz |
| S87 compute×1.5 A126 | S16约差13.47s | E1 CPU +1.395GHz |
| S87 compute×2 A126 | S49约差21.16s、S79约差18.41s等 | E2 CPU +2.877GHz、E1 CPU +1.299GHz |
| S88 compute×2 A126 | S42约差7.19s、S27约差6.17s等 | E1 CPU +0.765GHz、E2 CPU +0.675GHz |
| S88 deadline×0.8 A126 | S18约差2.21s | E2 CPU +1.642GHz |

数值结果支持：这些代表性**必要预检已通过但原Stage-1失败的候选**，确有任务期限与共享MEC CPU/带宽容量压力。**不能证明全部未评价候选都因此失败，不能将最小加权松弛解释成唯一因果，且虚构增加 MEC 容量后可行绝不是原物理实例严格可行。**

## 五、进一步确认原子动作的中间桥接作用

完整父子路径追踪确认：

- **S85/deadline×0.9/A126**：初始执行 `bundle_cross_uav::S54+S5->U2@15/13`，再执行 `task_mode::S75::local:None`，结果严格合格；不含原子算子的 plain4 对同一源失败，故“原子动作仅为末步不合格候选”并不意味着它不能作为有价值的中间桥接。
- **S87/compute×1.5/A125**：合格候选路径为 `bundle_new_contact::S36+S60->E1_C@15` → `cross_uav_fifo_relocation::S14->U4@4`。
- **S87/compute×1.5/A126**：合格候选路径为 `bundle_reuse_contact::S29+S36->G_U1_1` → `cross_uav_fifo_relocation::S77->U1@3`。

本轮总共 **5条 Stage-1 合格候选**含有原子操作祖先，来自若干相同或不同源结构；绝不能当作5个独立实例的增益。

## 六、结论与研发决策（与论文结论严格分开）

**两类瓶颈已被分别定位：**

1. **结构性候选不足**：强截止时间收紧时，必要队列预检的硬约束在大多数候选中无法解除；必须瞄准违约链及采集/上传位置，不能寄希望于词典序或更多 Stage1 求解。
2. **乐观筛选与严格资源失配**：在计算负载增加后，即使通过队列乐观下界，连续 CPU/带宽共享竞争仍让真实 Stage1 不合格；当前代理键一旦 `queue_passed`，往往只剩路径距离与**任意字符串字典序**，根本不反映接触批次/CPU紧张度。

**仅凭第5–8位严格可行解不能宣称算法提升**：此处人为支付了超过原本3次的 CVX 与Stage2求解，且只在一个已观察的源结构出现4条额外严格合格候选。因此不能合并 `develop`，也不能修改论文结果。

下一步最直接的可证伪研究方向是：**在完全相同3个 Stage-1候选名额中，只改变等代理分数时的 tie-break（复用接触优先或算子家族多样性），冻结源 D 对比成功率、CPU；再尝试低成本、与 MEC 批次/CPU 真实约束相关的候选评价，而非增加模糊的新邻域。** 任何选优策略一旦确定，必须在新的独立场景和等端到端预算下重新验证。
