# P1 原子联合候选失败诊断：冻结原始结果与反事实隔离实验

**基线不可变：** 原始 `develop` 提交 `0bdf3a26d4c042e13f96f84977261ffdd33cfc89`；P1 源实验 `0bfc189bffa89fdafc91877558e911aa12350641`，Actions `38134649545`。本实验分支 `experiment/p1-candidate-selection-diagnostics` 不改动论文正式算法、原始归档或基准图表。

## 1. 冻结的 22 个源失败结构，原始 JSON 独立复核

S85–S88、算法种子 A125/A126，共32个高压力状态，22个 `infeasible_precheck` 固定 D 满足实验入选标准。

| 修复方法 | 严格两阶段恢复 | 队列预检通过的源结构数 | 进入精确 Stage1 的候选数 | 精确 Stage1 合格候选数 | 平均修复时间 |
|---|---:|---:|---:|---:|---:|
| 原队列深度2 | 2/22 | 5/22 | 10 | 未逐候选存档 | 0.650s |
| 普通队列深度4 | 4/22 | 9/22 | 24 | 8 | 1.437s |
| 原子卸载深度4 | 3/22 | 10/22 | 25 | 6 | 1.501s |
| 原子卸载+双任务跨 UAV 深度4 | 4/22 | 11/22 | 28 | 9 | 2.039s |

严格恢复数与既有结论一致，`queue_passed` 取真实每臂原始诊断；这里的 **5/22、9/22、10/22、11/22** 指至少产生一个乐观预检合格候选的源状态，不是全模型可行率。

**原子候选漏斗：** 在已访问的 beam 状态上，原子卸载臂生成合法原子候选1296个，8个进入精确 Stage1，**0个严格合格**；允许跨 UAV 原子移动后生成2158个，8个进入精确 Stage1，仍 **0个严格合格**。两个臂只有最终标签为旧算子的候选产生 Stage1 通过。无法据此断言未被精确评估的原子候选也全部不可行。

原子策略 Stage1 判定为不可行的精确候选主要返回 `infeasible`，而不是 `optimal_inaccurate`；然而求解状态不能单独证明原问题全局不可行，队列必要下界本来也忽略跨 UAV MEC 资源争用。

## 2. 相反方向的两个配对样例

- **S85 / compute×1.5 / A125**：普通4步找到了 `fifo_predecessor_new_contact::S18::E1_C@16` 并完成两阶段合格修复；原子混合搜索第二层把候选名额导向 `bundle_new_contact`，其前三个精确候选均失败。说明原子候选可能挤占有效旧路径/solver 名额。
- **S85 / deadline×0.9 / A126**：普通4步没有候选通过必要预检；原子+跨 UAV 臂首层保留了 `bundle_cross_uav::S54+S5->U2@15/13`，此后生成最终一步为 `task_mode::S75::local:None` 的合格候选。提示原子移动**可能作为中间桥接**有作用，但最终严格合格的是复合搜索路径，不可归功于单个原子候选本身。

从冻结记录无法完整重建每个离散路径的父节点签名（旧记录主要保留可重复的 move 标签）；要严格证明是哪一条路径造成成功，需额外的逐候选签名/父子链审计。

## 3. 发现的汇总口径问题

`atomic_search` 输出 `queue_passed`、`beam_depth_reached`，但旧的 `run_atomic_batch_study.summarize` 和 `summarize_atomic_batch.aggregate` 读取 `precheck_passing` / `queue_pass_candidates` 与 `actual_depth`，会把原子臂预检和深度错误统计成零。这是**摘要键名不兼容**，不影响基于 `strict_both_recovered` 的恢复总数。优先修复统计，再做机制归因，不应因此重写原论文已有结果。

## 4. 预设的选择机制反事实实验

本实验分支在 `experiments/atomic_batch_search.py` 加入**默认关闭**的诊断选项，保持默认 P1 动作、约束与完整结果验收不变。同样从已冻结的22个源 D、beam width 2、最大4层、最多3次 Stage1 精确检查开始：

1. `plain4`：不含原子算子的原普通4步对照。
2. `atomic_global`：原原子+跨 UAV 全局排名方法，作为新代码回归对照。
3. `atomic_pure_beam`：仍生成原子候选，但中间 beam 只保留纯旧操作路径，检查代码/额外生成开销是否破坏普通搜索。
4. `atomic_protect_beam`：在两条 beam 中保证至少一条仍是纯旧操作路径，隔离中间搜索路径遭新原子候选排挤的影响。
5. `atomic_protect_shortlist`：仅在最终3个精确检查名额中保证至少一个来自纯旧操作路径，隔离终态候选排序/solver名额的影响。
6. `atomic_protect_both`：同时保护中间旧路径和最终旧候选。

每个臂在最终 Stage1+Stage2 与原有时序残差审计全通过才算真正恢复。增加保护规则会改变候选排序/生成开销，**固定 CVX 名额并不等于相同端到端墙钟时间预算**。本轮 S85–S88 已因事先检查结果转为研发样本；无论如何不得再次声称独立泛化验证。

## 5. 可能的后续决策

- 若保留旧路径能恢复 S85/compute×1.5/A125 但原子全局方法失败，说明原子与旧候选的**竞争**是可验证的具体瓶颈；仍要检查完整时间成本。
- 若更多严格合格恢复依旧主要来自纯旧操作路径，应优先把原子算子当作搜索辅助或停止常规展开，不因生成量大而宣称新结构贡献。
- 若保护候选也不改善，下一步才需要研究 CPU/带宽/EDF 批次真实资源违反信息指导任务配对，而非继续增大 beam 或随意增加邻域。
- 只有完整等端到端预算、更多未观察的新场景验证后，才可讨论替换正式 ESI-ALNS 的机制和论文创新。

以上均使用同一个源 D、同一个 Stage1/Stage2 严格验收规则、beam宽度2与 Stage1 候选检查上限3；生成量与实际墙钟耗时不同，因此不能把 4/22 当作等时间优势。全部22个压力失败源里，六种设置在**相同5个源**里合计产生可行恢复；原子与 plain4 两个差异事件互相抵消。

**S85 compute×1.5 / A125：** plain4 两个同名 `fifo_predecessor_new_contact::S18::E1_C@16` 不同结构中，第二个 Stage1 为 `optimal` 并最终两阶段合格。原子全局的 top3 却全部是 `bundle_new_contact`，三者 Stage1 `infeasible`。即使将原子臂的中间 beam 限定为纯旧操作路径，最终前三个精确求解名额仍被原子终态抢占，因此 `atomic_pure_beam` 失败。这是**候选终态排序/名额竞争可导致退化**的直接证据。

`atomic_protect_both` 最终确实给一个纯旧操作最终态留位，结果仍未合格：由于 beam 过程和候选的结构签名可能不同，最终一步标签相同并不能保证复制了原 plain4 的合格 D；一个保护名额不足以保证不会丢掉有效结构。它不能用于主张「只要保护一个名额就能修好」。

**S85 deadline×0.9 / A126：** plain4=失败，原子全局=成功，且 `atomic_protect_beam` 和 `atomic_protect_both` 均保留成功；纯旧路径 beam 版失败。首层原子双任务跨 UAV 状态出现在成功路径搜索范围内，最终精确合格候选末步是旧 `task_mode::S75::local:None`。说明成效可能依赖原子桥接，但还需要父子签名追溯来确认严格因果路径。

**S87：** 三个恢复案例所有六臂都成功。**S86和S88：** 六臂全部0成功；说明即使在当前已观察到的压力场景下，不是通过简单 beam/shortlist 容错就能解决大多数 MEC 资源耦合失败。

### 正式决策

1. **不合并 P1 原子邻域到 `develop`，也不修改论文结果**。独立旧记录和这一轮进一步研发诊断均不足以证实净收益。
2. 单纯恢复旧算子一个候选名额并不能解决问题；需要先实现严格的**候选签名+父子路径追踪**，区分原子动作作为中间桥接与直接可行终态的作用，再判断有哪些旧可行状态被压制。
3. 真实瓶颈不只是搜索深度：当前队列乐观下界可以通过、Stage1依然 `infeasible`。下一机制应针对 MEC CPU/带宽与上传批次时序的具体冲突，并匹配真实严格候选评价成本。
4. 这一批 S85–S88 已经反复观察，之后任何选优新算法必须另用未见场景完成**全算法端到端等预算验证**。
