# P3：基于静态共享 MEC CPU 必要约束的任务级修复目标诊断

> 研发协议冻结于该分支的首次验证 Actions 中。本轮只使用此前已研究过的 S85–S88 四个场景（每场景算法种子125/126），严禁称为独立新样本或最终论文算法。原始 `develop`、旧数据和正式论文结果均保持不变。

## 一、科学问题、与已完成 P2 的关系

P2 从原 P1-R 的静态 `F_(UAV,MEC)` 和强制 FIFO/EDF 顺序推得共享 CPU 必要下界，不需要调用CVX，即可在已严格评价过的42个乐观队列预检合格候选中，额外安全识别23个不满足该必要条件的固定 D；原有13个严格合格对照无误拒。P2 将其用于等精确候选名额的筛选，研发样本恢复数 4→5/22、接口调用28→16。然而这仍主要是**负向判定/剪枝**，并不说明算法能够生成新的有效 D。

本轮 P3 转向：**能否根据违反 CPU 必要条件的 MEC、虚拟队列及其绑定前缀任务，选择更有针对性的卸载/接触/跨 UAV 修复操作？** 与随机或单纯计算量最大的任务选择相比，能否创造更多真正严格可行的结构？

## 二、使用了什么新的操作？怎样保持对照可解释？

计算每个站点的最小静态 CPU 需求 `sum(F_pair_lb)` 及压力比；选择压力最大的站点与虚拟队列，找到下界中达到最大需求的任务前缀。从此前缀选择绑定截止时间任务和高工作量前驱，最多三个目标。

每个目标仅执行四类与原物理约束一致的操作：

1. 计算模式由 MEC 转为本地；检验是否将冲突转移至本地 FIFO。
2. 在同一 UAV 既有的后续接触中，重定向至其它 MEC。
3. 仍满足最大接触次数时，新增一个其它 MEC 的接触并转移卸载。
4. 将当前卸载任务跨 UAV 转移，形成另一 UAV 的本地 FIFO 任务。

均需原离散结构合法性校验、去重；绝不将下界改善直接视为通过 Stage-1/Stage-2。

本轮设计四臂，均起始于同一个原始失败 D：

| 实验臂 | 原队列+原子动作 | 新增四类操作 | 选择目标依据 | Beam 容错 |
|---|---|---|---|---|
| `old_atomic_cpu_guard` | 是 | 否 | 原方法 | 全局原排序 |
| `cert_plain` | 是 | 是 | **真实静态 CPU 下界绑定前缀** | 全局原排序 |
| `cert_bridge` | 是 | 是 | 同上 | 保留一条确实降低 CPU 下界超额且不越过受控队列超额的中间搜索路 |
| `heavy_bridge` | 是 | 是 | **同数量的全局最高计算负载卸载任务** | 相同 CPU 进展保留规则 |

关键消融：`cert_bridge` 对 `heavy_bridge` 才是 **证书指向任务是否有额外价值** 的对照；`cert_plain` 对 `cert_bridge` 才能隔离 CPU 进展 Beam 保护策略。原队列/原子候选池与其它操作均不改。

每个方法搜索最多4层、Beam宽度2、候选生成4秒软上限、每个源 D 最多3次原 Stage1 CVX 精确评价；继续使用 P2 **安全必要 CPU 界**作精确评价前的拒绝，最终仍须通过完整原 Stage1/Stage2、保存及重构的时序资源残差。完整报告候选生成时间、证书时间、精确接口调用次数与实际总耗时；软上限不是实际相同墙钟时间。

## 三、文献研究的审慎定位

- Kasapidis et al., **A unified solution framework for flexible job shop scheduling problems with multiple resource constraints**, *European Journal of Operational Research*, 320(3), 479–495 (2025), DOI: [10.1016/j.ejor.2024.08.010](https://doi.org/10.1016/j.ejor.2024.08.010). 已有带多资源约束与反馈引导的 ALNS-CP；“资源感知 ALNS”笼统表述没有首创性。
- **More powerful energetic reasoning for the cumulative scheduling problem**, *Discrete Applied Mathematics*, 378, 187–209 (2026), DOI: [10.1016/j.dam.2025.07.016](https://doi.org/10.1016/j.dam.2025.07.016). 资源能量推理/必要条件是成熟思想；P2 约束是源模型中**静态配额、单对虚拟队列**的特化，不能宣称新创可行性界通法。
- Barzanjeh et al., **Logic-based benders decomposition algorithm for robust parallel drone scheduling problem considering uncertain travel times for drones**, *Transportation Research Part E*, 193, 103877 (2025), DOI: [10.1016/j.tre.2024.103877](https://doi.org/10.1016/j.tre.2024.103877). 已有无人机调度中的分解反馈与有效割。我们当前仅实现启发式反馈与必要预检，**尚未构造 Benders 割**。

潜在方法差异仅在：面向原多 UAV 路径—接触—卸载—静态 MEC 份额—本地 FIFO/远端 EDF 的具体 **约束证书→目标任务/邻域动作映射**，而非把约束判定或算子名称视为创新。

## 四、明确的失败/成功门槛

**可继续条件（本轮仅为机制筛选）：** CPU 证书定向修复在相同求解名额上对比同算子族、同目标数量的全局重任务对照，有真实严格恢复增益，且不只是付出明显更多总墙钟时间；对未改善实例能解释是候选生成不足、Beam丢弃、必要界仍不充分，还是 Stage1 共享带宽与时序失败。

**需要停止或换方向：** 如果同族证书定向不优于负对照、原有成功被破坏或候选生成耗时远高于收益，就不要仅凭下界数学安全而把这组新操作升级为论文主算法。转而研究更强的共享时序/通信必要界或更可信的连续资源代理，而不是继续叠加大邻域。

**真正对外发表的最低门槛：** 先冻结新机制，再在从未用于研发的独立场景和不同任务规模进行真正等端到端预算 B-ALNS / 原始 ESI / 新方法对照，完整报告失败、超时、条件能耗、消融、操作成本与样本层级；不把算法种子当成独立场景重复。

### 可追溯的成功链案例

- **S86/deadline×0.9/A125**，源固定D共享静态CPU超额指标约3.05；原 P2 方法严格失败。证书目标组在第2层接受 `cpu_target_local::S50` 作为暂时结构，随后再通过 `bundle_reuse_contact::S12+S16->G_U1_1` 形成 Stage-1 `optimal` 及完整Stage2合格候选。说明**证书指定任务并非必须是最后一步操作，它可以改善后续搜索状态**。
- 相同源D下，`heavy_bridge` 通过 `cpu_target_cross_local::S58->U5@5` 等非证书任务也能得到合格解，证明“只靠CPU证书指向”并非解决此例的唯一机制。
- **S85/compute×1.5/A125** 源CPU超额为0（虽然队列必要时间下界仍失败）：证书组保留旧 `bundle_reuse_contact::S41+S18->G_U5_1` 成功路径；全局重任务组提前被 `cpu_target_cross_local::S5` 等操作改变Beam而丧失该成功。此例说明候选扩张有替换风险。

### 研发判断

新操作有结构搜索潜力，却尚不值得直接合并：**增益1例、实际CPU成本上升、四类压力中 compute×2 / deadline×0.8 仍0严格恢复**。下一步只应将现有策略**冻结后作独立新场景反证检验**，至少比较 `cert_plain`、`cert_bridge`、`heavy_bridge` 与原CPU预检基线，且将总时间放在与恢复率同等重要位置；不能再反复用这四个场景微调参数并把它们称为独立样本。

## 六、补充根因复核：为何高负载难题尚未解决？

将 P3 的22个固定失败源与 P2 的原始相同SHA-256对象重新关联（只看独立的 B-ALNS 源，不将相同源 B/ESI 重复计数）：

- **22/22** 源固定 D 已经被 FIFO/EDF 乐观时限必要条件拒绝，故 CPU 份额必要下界并不是这些**源 D 的独立首个可行性失败信息**。
- 其中 **21/22** 源 D 同时违反共享 CPU 份额必要界，余下1个 CPU 下界通过但 FIFO/EDF 时间下界失败。
- 在 `deadline×0.8` 的8个 B-ALNS 尝试中，有 **6/8** 个源 D 出现至少一个虚拟对在乐观首个 MEC 批次开始时就无法给某前缀任务留出正计算时间窗口，所需CPU下界因此无穷。这意味着**仅向某 MEC 增加计算能力无法修复该固定 D**，应优先改变任务采集/接触到达顺序、任务执行位置或路线，而不能把无穷CPU压力理解为“再多分配 CPU”。
- `compute×2` 的8个原始 B-ALNS 源全部既违反队列必要条件、也违反CPU份额必要界；有限资源/排队冲突高度重合，因此只迁移一个绑定CPU任务未必能消除全部任务完成期限问题。

这一结果解释了为什么 P3 在 `deadline×0.8` 和 `compute×2` 仍是0个恢复：根源经常是**多类先验硬约束同时不满足**，而非“CPU容量剪枝正确”就代表“一步CPU任务迁移可以恢复”。严禁由这些源级关联推断整个实例数学无解。

更合理的下一轮机制应是**分阶段诊断触发**：先处理 FIFO/EDF、采集/接触到达的时间窗口必要冲突；只有候选越过时间必要界后，再针对共享静态 MEC CPU 份额作安全拒绝和候选重排。须与“直接使用同一证书无条件生成更多操作”进行相同完整计算预算消融。
