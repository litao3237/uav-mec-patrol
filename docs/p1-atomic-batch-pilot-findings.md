## 科学问题与协议

之前的“源头任务时延桥接”在旧 S61–64 样本看起来优于同深度搜索，但在新 S81–84 样本中完全未重复。即，仅增加 beam 深度或“允许暂时不合格中间解”不足以使高负载联合资源问题可靠可行。

本轮利用 **原始 S81–84 检查点**（曾用于上一轮桥接评估，因此只能算研发样本），从每个 `infeasible_precheck` B-ALNS 离散结构出发，测试如下四臂：

| 实验臂 | 固定队列依赖算子 | MEC 双任务原子卸载/提前拆批次 | 两任务跨 UAV 同步转移 | Beam 深度 | CVX Stage-1 候选上限 |
|---|---|---|---|---:|---:|
| `queue_original_depth2` | 是 | 否 | 否 | 2 | 3 |
| `queue_plain_depth4` | 是 | 否 | 否 | 4 | 3 |
| `atomic_offload_depth4` | 是 | 是 | 否 | 4 | 3 |
| `atomic_offload_and_cross_uav_depth4` | 是 | 是 | 是 | 4 | 3 |

全部从同一个源 D 开始，严格 Stage-1、Stage-2 与保存/重建两条时序残差完全不放松，独立执行、完整记录 CPU。所有4步方法使用**相同**的旧队列必要下界排名、beam width 2、最长4秒候选生成软上限，并只对不被乐观时间下界拒绝的最优3个候选调用 Stage-1 oracle。唯一变量是原子候选家族是否加入。

## R1：4个场景、22个失败源结构

| 方法 | 严格 Stage1+Stage2 修复成功 | 每源失败结构平均完整耗时 | 与同深度 plain4 相比 |
|---|---:|---:|---|
| 原队列2步 | **2/22** | **0.616秒** | 低深度参考 |
| 普通队列4步 | **3/22** | **1.082秒** | 同深度对照 |
| 双任务本地→MEC 原子卸载 + 批次调整 | **3/22** | **1.519秒** | **没有额外修复** |
| 再加两个任务同步转移至另一 UAV | **3/22** | **1.862秒** | **没有额外修复** |

严格恢复的源结构完全相同：S81 一个、S84 两个，S82/S83 都没有恢复。atomic 只是提高了计算时间而未改善成功覆盖。

## 候选审计：新邻域确实生成和进入精确评价

为了避免错误地把无效结果归咎于代码开关未生效，基于 **四个完整 archived JSON** 重新统计候选名额：

- `atomic_offload_depth4` 的最终严格 oracle 候选中，`bundle_reuse_contact` 共 **14 次**，其中 **3 次**候选通过 Stage-1；`bundle_early_split` 共 **3 次**，Stage-1 通过 **0 次**。
- `atomic_offload_and_cross_uav_depth4` 的 `bundle_reuse_contact` 被选中 **17 次**，其中 **3 次** Stage-1 通过；它生成了大量合法 `bundle_cross_uav`，但这一家族**没有进入前3个严格候选名额**。
- 旧 queue-plain4 的单任务跨 UAV 重定位被严格评价 **6 次**，其中 **4 次** Stage-1 通过；其它有效案例还涉及 `fifo_predecessor_new_contact`。
- 四步 atomic 方法的确可在若干病例找到新的 Stage-1 通过候选，但没有增加最终两阶段严格可行恢复数。

因此，至少本轮代码不只是“算子未启用”。真正的短板可能是：**更多候选争夺仅3个严格 Stage-1 oracle 名额、共享 MEC CPU/带宽的联合约束远强于独立乐观队列下界、双任务一起进入一个 MEC 批次可能反而提高远端资源竞争。** 这些都只是合理机制假说，尚非因果证明。

## 科研决定

该方法应保持**实验性质、不可写成已经成立的论文创新**，不能把「增加两个局部调整」解释为解决了路径—接触—卸载的资源耦合问题。

新场景 S85–S88、种子125/126的独立验证已按上述冻结操作家族和精确评价上限启动：
https://github.com/litao3237/uav-mec-patrol/actions/runs/38134649545

*在这组结果出来之前，不再根据 pilot 结果更改候选排序或算子阈值。* 无论新场景结果是否改善，都如实保留严格恢复率、CPU时间、分场景条件和完整求解状态。

之后是否继续做更复杂的原子邻域，应先评估：**在合法的 MEC 接触/卸载结构里，到底是否存在多个原子候选真正严格可行、但被原来的代理排在候选名额外**，而不应凭空增加更大的邻域。
